# caddy agent context

For general k3s/Helm conventions (chart structure, values layout, secrets,
networking, backups), see `machines/pax/k3s/AGENTS.md`.

## Read this when

Editing anything under `apps/caddy/`: templates, values, the shared PVC,
or the Caddyfiles in the public/private ConfigMaps. The chart deviates
from the standard one-Deployment pattern in ways the stack guide does not
cover.

## Architecture

The chart deploys **two Deployments from one chart**, generated by a
`range` over `list "public" "private"` in `templates/deployment.yaml`:

- **caddy-public** — binds host IP `172.16.0.5` (eth0, public VNet) and
  serves `*.guneet.dev`. Image: `caddybuilds/caddy-cloudflare`.
- **caddy-private** — binds host IP `100.100.1.3` (tailscale0) and serves
  `*.guneet.xyz`. Image: `kvqn/caddy-cloudflare-l4` (the L4 build is
  required for the layer4 TCP proxy that fronts `dev-db` Postgres on the
  private side; do not swap it for the plain Cloudflare build).

Both deployments share **one PVC**: `caddy-data` (`ReadWriteOnce`,
defined in `templates/shared-pvc.yaml`). RWO works only because both
pods are pinned to the same node via `nodeSelector: role=primary`. The
PVC stores Caddy's TLS certificate cache.

If node pinning is ever removed, this PVC **must** be split per variant
or switched to `ReadWriteMany`; the inline comment in `shared-pvc.yaml`
states the same constraint.

## Routes live in templates, not values

Unlike most charts, public and private route tables are not in
`values.yaml`. They are inline Caddyfiles inside:

- `templates/public-configmap.yaml` — all `*.guneet.dev` routes
- `templates/private-configmap.yaml` — all `*.guneet.xyz` routes

Adding or changing a route means editing the relevant Caddyfile in the
template, then:

```sh
kubolt validate          # from machines/pax/k3s/
kubolt install caddy
```

Cross-app backends use the shared-values DNS pattern:
`{{ .Values.apps.<name>.appName }}.{{ .Values.apps.<name>.namespace }}.svc.cluster.local:{{ .Values.apps.<name>.port }}`.
Never hardcode service DNS names in the Caddyfile.

## registry-public write authentication

The `cr.guneet.dev` route in `public-configmap.yaml` enforces basic auth
on registry **writes** only (`POST`, `PUT`, `PATCH`, `DELETE` on
`/v2/*`). Anonymous reads stay open so pull-through works.

The basic_auth directive references two env vars wired into the
caddy-public pod from the `registry-public-basic-auth` Secret:

- `REGISTRY_PUBLIC_USERNAME` — basic_auth user
- `REGISTRY_PUBLIC_HTPASSWD` — bcrypt hash (the Caddyfile passes the
  hash directly to Caddy's `basic_auth` directive)

Both come from Obscuro keys of the same name. The plaintext
`REGISTRY_PUBLIC_PASSWORD` is stored in Obscuro too, but it is not
mounted into any pod, it exists only for operator records and
`docker login` documentation.

Rotating the password requires:

1. `obscuro set REGISTRY_PUBLIC_HTPASSWD` with a freshly generated
   bcrypt hash, and `obscuro set REGISTRY_PUBLIC_PASSWORD` with the
   matching plaintext.
2. `kubolt install caddy` to roll the caddy-public pod with the new
   secret (the deployment uses a `checksum/secret-basic-auth`
   annotation that triggers a rollout when the secret changes).

## Matrix `.well-known` delegation

The public Caddyfile serves the Matrix federation discovery endpoints
**inline** under `matrix.guneet.dev`:

- `/.well-known/matrix/server` returns
  `{"m.server": "matrix.guneet.dev:443"}`
- `/.well-known/matrix/client` returns
  `{"m.homeserver": {"base_url": "https://matrix.guneet.dev"}}`

These are static `respond` directives in caddy, not proxies to synapse.
If synapse's `server_name` or federation port ever changes, the fix
goes here in the **caddy** Caddyfile, not in the synapse config. Keep
both in sync.

The same `matrix.guneet.dev` host also reverse_proxies all other paths
to the synapse service with a 100MB body limit.

## TLS

Both instances use Caddy's Cloudflare DNS-01 ACME challenge. The
Cloudflare token comes from the `CLOUDFLARE_API_TOKEN` Obscuro secret,
mounted as an env var from the `cloudflare-secret` Secret. Certificates
land in the shared `caddy-data` PVC at `/data` inside the container.

## Validate

From `machines/pax/k3s/`:

```sh
kubolt validate
kubectl get pods -n caddy
kubectl get pods -n caddy -l app=caddy-public
kubectl get pods -n caddy -l app=caddy-private
```

`kubolt validate` renders both Deployments and both ConfigMaps and
fails on any template error or missing shared-value reference.

## Do not

- **Do not change the `bind` IPs** (`172.16.0.5`, `100.100.1.3`). They
  are host-specific interface addresses for the `pax` node. Changing
  them silently breaks all routing.
- **Do not put `*.guneet.xyz` routes in `public-configmap.yaml`** or
  `*.guneet.dev` routes in `private-configmap.yaml`. The split exists so
  internal services are not exposed on the public VNet.
- **Do not remove `templates/shared-pvc.yaml`** without first changing
  both deployments to mount separate PVCs (or `ReadWriteMany` storage).
  RWO with two deployments only works because of node pinning.
- **Do not drop the `kvqn/caddy-cloudflare-l4` image** on caddy-private.
  The layer4 proxy block for `dev-db` Postgres requires it.
- **Do not hardcode service DNS names** in either Caddyfile. Always use
  the `.Values.apps.<name>` shared-values pattern.
